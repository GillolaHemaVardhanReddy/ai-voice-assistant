## Atom P1.5.0 — First endpoint (`service/main.py`)

💡 **Idea:** FastAPI is Express rearranged. `app.get('/ask', handler)` becomes `@app.get("/ask")` above the function — the same handover, different placement.

💻 **The lines that matter:**
```python
from fastapi import FastAPI
app = FastAPI()                 # ≡ const app = express()

@app.get("/health")
def health():
    return {"status": "ok"}     # a returned dict IS the JSON response — no res.json()
```
```bash
uvicorn service.main:app --reload      # file service/main.py → variable `app` inside it; --reload = nodemon
```

⚠️ **Gotcha — why TWO packages (`fastapi` + `uvicorn`) when Node needed only `express`:**
Node ships an HTTP server *inside the runtime* (`http.createServer`), so Express is only a router layer and `app.listen()` borrows Node's server. **Python's runtime has no production HTTP server.** So the job splits:
- **FastAPI** defines the app (routes, validation, docs) — never touches a socket.
- **uvicorn** *is* the server — opens the port, speaks HTTP, calls your app.

The contract between them is **ASGI** — a standard signature, so any ASGI server can run any ASGI framework. **ASGI is async; its sync ancestor is WSGI, which is what Flask speaks.** That protocol difference is the actual reason `await asyncio.wait_for(...)` (the Session-7 hang fix) only exists on the FastAPI side.

📌 **Free win:** `http://127.0.0.1:8000/docs` — auto-generated Swagger, zero config. Same output as the `swagger-autogen` tool he published, except nothing to run.

❓ **Self-test:** Why does a Python web app need a separate server package when a Node one doesn't?
<details><summary>answer</summary>Node's runtime includes an HTTP server; Express is just routing on top of it. Python's doesn't, so uvicorn provides the socket/HTTP layer and calls the framework through the ASGI contract.</details>

## Atom P1.5.1 — Typed request body (Pydantic)

💡 **Idea:** **the class is a doorman with a checklist.** It's checked *before* your function runs — so an invalid request never reaches your code.

💻 **The lines that matter:**
```python
from pydantic import BaseModel

class AskRequest(BaseModel):
    question: str               # the checklist: body must have `question`, and it must be text

@app.post("/ask")
def ask(body: AskRequest):      # this type hint is the INSTRUCTION, not documentation
    return {"you_asked": body.question}
```
One class replaces three Node packages: `express.json()` (parse) + `zod`/`joi` (validate) + `swagger-autogen` (document).

⚠️ **Gotcha 1 — the class *is* the public API contract.** Whatever you name the field is the required JSON key. He typo'd **line 9** (`queston: str`), sent the correct `{"question": ...}`, and got a 422 — the error was right, the class was wrong.

⚠️ **Gotcha 2 — read a 422 as a path.** `"loc": ["body", "queston"]` = *in the body → the field `queston`*, outside-in like a filesystem path. `"input"` echoes what you actually sent. Compare the two and the bug names itself.

⚠️ **Gotcha 3 — extra fields do NOT behave like missing ones:**
| sent | default (`ignore`) | `extra="forbid"` |
|---|---|---|
| missing / wrong type | 422, function never runs | 422 |
| **extra** field | **silently dropped**, request succeeds | **whole request rejected** |

Either way **the extra value never reaches your function.** `forbid` doesn't drop harder — it refuses the visitor entirely. Knob: `model_config = ConfigDict(extra="forbid")`.

📌 **Why a class can validate at all (the JS contrast):** TypeScript types are **erased** at build — that's why you need `zod` to restate the same shape. **Python keeps annotations as real runtime data**, so Pydantic reads `question: str` while the program runs. Inspect it yourself: `print(AskRequest.model_fields)`.

❓ **Self-test:** You send `{"question": "hi", "hacker": 123}` to a default model. What comes back, and what is `body.hacker`?
<details><summary>answer</summary>The request succeeds and the answer is normal. <code>hacker</code> was dropped at the door — <code>body.hacker</code> doesn't exist. With <code>extra="forbid"</code> the same request would 422 instead.</details>

## Atom P1.5.2a — The retriever, over HTTP

💡 **Idea:** two walls sit between a script and a service — **Python must be able to *find* your module**, and **whatever you return must be a type JSON can hold.**

💻 **The lines that matter:**
```python
import sys
sys.path.append("learn/phase2")     # MUST come before the import — imports run top-to-bottom
from store import search

@app.post("/ask")
def ask(body: AskRequest):
    hits = search(body.question, k=3)
    return {"hits": [
        {"score": float(score), "chunk": chunk, "source": source}   # float() is the whole fix
        for score, chunk, source in hits
    ]}
```

⚠️ **Gotcha 1 — how Python finds modules.** It does **not** search your project, and it does **not** walk up looking for `node_modules` like Node. It checks a plain list of folders, `sys.path` (launch dir → stdlib → venv `site-packages`), and gives up. Not on the list = doesn't exist. (`print(sys.path)` to see it.)

⚠️ **Gotcha 2 — importing a module RUNS it.** `from store import search` executed all of `store.py`: loaded MiniLM into RAM, globbed 6 files, chunked to 127, embedded all 127 — *then* handed over `search`. Visible as a suddenly-slow startup. **Once at startup, not per request** — good for latency, but it *is* the cold-start bill on a sleeping free tier.

⚠️ **Gotcha 3 — JSON has six types: string, number, boolean, null, array, object. `numpy.float32` is none of them.** Returning the raw `search()` tuples → 500, `TypeError: 'numpy.float32' object is not iterable`. Same class of bug as returning a Mongoose doc or a `Date` straight out of an Express handler: **anything crossing the serialization boundary must be a plain type.**

🔎 **Traceback skill (2nd time now):** the useful line was the **very first**, `TypeError: 'numpy.float32'…`; the ~60 lines below were starlette/uvicorn rewrapping it. **Read the first anomaly, not the bottom.**

📌 **The rule that explains why only `score` broke:** *a value's type comes from what made it.* `chunk`/`source` were read from text files ⇒ plain `str` ⇒ already legal JSON. `score` came out of `vecs @ q` ⇒ **numpy math makes numpy numbers**. It printed as `0.544` all through Phase 2 — `print()` hides types, and this was the first time it mattered.

⚠️ **Known debt, flagged not hidden:** `sys.path.append("learn/phase2")` is relative to *where uvicorn was launched* (repo root) — the same assumption `store.py` already makes with `glob.glob("learn/phase2/notes/*.txt")`. Fine locally; must be fixed before deploying.

❓ **Self-test:** `search()` returns `(score, chunk, source)` and only `score` needed `float()`. Why?
<details><summary>answer</summary><code>chunk</code> and <code>source</code> are plain Python strings — <code>str</code> is already a JSON type. <code>score</code> came out of a numpy operation, so it's a <code>numpy.float32</code>, which JSON has no concept of.</details>

## Atom P1.5.2b — The LLM answer, over HTTP

💡 **Idea:** **a script's job is to print; a service's job is to return.** Same logic, opposite output channel.

💻 **The line that matters** — in `rag.py`, at the end of the `try`:
```python
        return s        # `s` was already accumulating the streamed answer — it was just never handed back
```
```python
# service/main.py
from rag import answer

@app.post("/ask")
def ask(body: AskRequest):
    return {"answer": answer(body.question)}
```

⚠️ **Gotcha — the owed `return None` bug from Atom 2.8 turned fatal here.** In a script, "prints but returns `None`" costs you a stray `A: None`. In a service it means the caller gets nothing, because **nobody is standing at the server's terminal reading `print()`.**

📌 **No second MiniLM load:** `rag.py` also does `from store import search`, but **Python caches imported modules** — the module object already in memory is reused. Import cost is paid once per process, not once per import statement.

❓ **Self-test:** Why was `return None` harmless in `rag.py` as a script and fatal in the API?
<details><summary>answer</summary>The script's real output was the streamed <code>print()</code> to a terminal a human was watching. Over HTTP the terminal is on the wrong machine — the only thing the caller ever sees is the return value.</details>

## Atom P1.5.3 — Fail honestly (`HTTPException`)

💡 **Idea:** **never lie to your caller with a status code.** A swallowed exception + a `None` return means the API answers **200 OK** with `{"answer": null}` — "success, here's nothing."

💻 **The lines that matter:**
```python
from fastapi import FastAPI, HTTPException

result = answer(body.question)
if result is None:
    raise HTTPException(status_code=502, detail="Upstream model unavailable. Try again.")
return {"answer": result}
```

- **`raise`, not `return`** — FastAPI catches `HTTPException` and turns it into a real HTTP response. It's your `return res.status(502).json(...)`.
- **502 Bad Gateway, not 500** — *your* server is healthy; the thing *behind* it (OpenRouter) failed. A 500 would blame your own code and send you debugging the wrong box.

⚠️ **Cost of the silent version:** the React widget renders a blank box, the recruiter sees nothing, and the only evidence is a `FAILED:` print on a server terminal nobody watches. **In a script a swallowed error costs a confusing print; in a service it costs a silent failure at the far end of a network.**

📌 **Verified by breaking it on purpose** — corrupted `OPENROUTER_API_KEY` in `.env` → real `502` + `{"detail": "Upstream model unavailable. Try again."}`.

📌 **Swagger said "Undocumented"** next to the 502 — the OpenAPI schema only knows what you declare. Declaring it is `responses={502: {...}}` on the decorator. (Parked.)

⚠️ **Named as a band-aid, deliberately:** detecting failure via `is None` only works *because* `answer()` swallows its own exception. The real fix is the principle **libraries raise, callers decide** — `answer()` has no business hiding errors from whoever called it. Do that refactor together with the async timeout.

❓ **Self-test:** Why 502 and not 500?
<details><summary>answer</summary>500 = "my code broke." 502 = "I'm a healthy gateway, but the service behind me failed." OpenRouter being down is not your bug, and the status code should point the on-call person at the right box.</details>

## Atom P1.5.4 — Safety: CORS · rate limit · spend cap

💡 **Idea:** **layer cheap imperfect limits, then put one hard financial stop at the bottom.** No single layer has to be perfect.

| Layer | What it actually does | What it does NOT do |
|---|---|---|
| **CORS** | stops *other websites* embedding your bot in a browser | stop anyone — `curl` ignores CORS entirely |
| **Rate limit** | friction: N requests per IP per minute | help when many real users share one IP |
| **Spend cap** | hard ceiling on money | — this is the only one that can't be argued around |

💻 **The lines that matter:**
```python
from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(CORSMiddleware,
    allow_origins=["http://localhost:5173", "https://hemavardhanreddy.vercel.app"],
    allow_methods=["POST"], allow_headers=["*"])

from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
limiter = Limiter(key_func=get_remote_address)      # key_func = WHAT YOU COUNT BY — the only real decision
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

@app.post("/ask")
@limiter.limit("20/minute")                          # BELOW @app.post — decorators apply bottom-up
def ask(request: Request, body: AskRequest):         # slowapi REQUIRES a param literally named `request`
```
+ OpenRouter dashboard: a **separate** key for prod with a **$1/day** limit.

⚠️ **CORS is hygiene, not defense.** `allow_origins=["*"]` grants no *new* power (curl could always call you) — it removes *friction*, so any site can spend your credits from its visitors' browsers.

⚠️ **Rate limiting by IP is unfair to shared networks** (a college or office behind one public IP looks like one person). Mitigations, ranked: be generous (20/min, not 5) → add a **global daily cap** (immune to the shared-IP problem) → per-session keys (weak; clearable) → **the spend cap is the real backstop.**

⚠️ **slowapi's counter lives in process memory** — so 2 uvicorn workers = 2 counters = double your stated limit, and a restart wipes them. Fix at scale: point it at **Redis** (same as `express-rate-limit`'s Redis store). Size was never the issue; *sharing* and *durability* are.

📌 **Separate prod key ⇒ separate revocation.** A leaked deploy key is killed alone; local work and everything else keep running. **Blast radius.**

❓ **Self-test:** Your 429 came back without any OpenRouter call. Why?
<details><summary>answer</summary><code>@limiter.limit</code> sits below <code>@app.post</code>, so it wraps <code>ask()</code>. The wrapper checks the counter and raises <em>before</em> your function body runs — a blocked request costs nothing.</details>

## 🔧 Debugging skills earned here (both reusable)

**1. "Crashed at import" has a signature.** Port not listening **+** worker RSS stuck ~10MB = **died during import**, not "still loading." A process genuinely loading a model *grows*. Two cheap external signals beat reading code.

**2. Traceback rule, corrected.** Not "read the first line" — that was luck:
> **Find the frame that names YOUR file, and the message that names something YOU wrote.** Everything else is library plumbing.

Numpy case → the useful line was **first** (`numpy.float32`, your value). slowapi case → it was **last** (`main.py line 35`, your function). **Yours, not first.**

**3. Decorators are not decoration — they run at import.** `Exception: No "request" argument on function "ask"` fired while Python was merely *reading* `main.py`. Nothing had called `/ask`. That's `ask = limiter.limit("20/minute")(ask)` executing the instant the `def` finished, inspecting the signature, and refusing.

## Atom P1.5.5c/d/e — Docker 🐳

💡 **Idea:** a `Dockerfile` is a **recipe for a machine**. You're not shipping code that runs on a server you configured — you're shipping the server itself.

💻 **The whole file:**
```dockerfile
FROM python:3.10-slim
WORKDIR /app
RUN pip install --no-cache-dir torch --index-url https://download.pytorch.org/whl/cpu
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
RUN python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('all-MiniLM-L6-v2')"
COPY service/ ./service/
EXPOSE 8000
CMD ["uvicorn", "service.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Line by line:**
- `slim` = Debian with the extras stripped (~150MB vs ~1GB). **Image size costs TIME, not memory** — push, deploy, cold start. RAM (the 938MB RSS) is a *different* number.
- **CPU torch first, from PyTorch's own index.** Proven on his own disk: his venv had `torch 2.13.0+cu130`, `cuda available: False`, and **2.7GB of unused `nvidia/` libraries** (venv total 5.0GB). Result: image **1.95GB instead of ~5GB.**
- **`RUN` = build time (baked into the image); `CMD` = container start.** When the CMD process exits, the container dies — the container *is* that process.
- **Pre-downloading MiniLM at build** moves 90MB out of the first user's request. Same instinct as the keep-warm cron, pushed all the way to build time.
- **`--host 0.0.0.0` is mandatory.** Default `127.0.0.1` = "only from this machine", and inside a container that's nobody. **The most common Docker + web framework mistake:** unreachable server, perfectly healthy logs.
- **`CMD` as a list (exec form), not a string.** A string runs `/bin/sh -c "..."`, so the *shell* becomes the main process and usually swallows `SIGTERM` → Docker waits 10s then kills mid-request. Exactly Node's `execFile(cmd, [args])` vs `exec("string")`.

⚠️ **Layer caching — why the line order looks backwards.** An image is a stack of layers, one per instruction. A rebuild reuses layers top-down until one's input changed, then re-runs **everything below**. So: **order from least-likely-to-change to most-likely-to-change.** Code last.
- code last → edit `main.py` → rebuild in **seconds** (proven live)
- `COPY . .` first → edit `main.py` → **~15 min**, reinstalling torch every time
- Identical to Node's `COPY package*.json ./` → `npm ci` → `COPY . .`
- Invalidation rule: a layer dies from a change **to itself or anything above it.** Nothing below can touch it.

⚠️ **`.dockerignore` — the build context.** Before running any instruction, Docker packs the whole folder and ships it to the engine. Repo root held a **5.0GB** venv. With `.dockerignore` (`venv/ .git/ learn/ docs/ __pycache__/ *.pyc .env`) the transfer was **29.69 kB**.

🔒 **Why `.env` is in `.dockerignore` even though nothing copies it:**
1. **Future you** writes `COPY . .` for convenience and the key silently ships to a **public** Space.
2. **Images never forget.** Every layer is permanently inspectable — a secret in layer 4 deleted in layer 7 **is still in layer 4** and anyone who pulls the image can read it. The only fix for a leaked secret is **a new key**.
> 💡 **Secrets go in at RUNTIME, never at build time.** `--env-file .env` (locally) / the Space's Secrets panel (deployed) put the key in memory, never in a layer.

💻 **Running it:**
```bash
docker build -t recruiter-bot .          # the trailing "." is the build context, not decoration
docker run --rm -p 8001:8000 --env-file .env recruiter-bot
```
`-p host:container` · `--env-file` injects secrets at start · `--rm` deletes the dead container.

🏆 **The bug the container caught that the laptop hid.** `main.py` still had `sys.path.append("learn/phase2")` + `from store import search`. **Locally it worked** — the lesson folder was right there, so the service quietly loaded **two** copies of the store (RSS crept 938 → 994MB). **In the container it crashed instantly**, because `.dockerignore` excluded `learn/`.
> 💡 **A container is a clean room. It surfaces every hidden dependency your laptop was quietly providing.** This is why "works on my machine" stops being a sentence anyone has to say.

❓ **Self-test:** Why does `COPY service/` come *after* both `pip install` lines?
<details><summary>answer</summary>Layer caching. Code changes constantly; dependencies don't. With code last, editing <code>main.py</code> invalidates only the final layer — rebuild in seconds. Copy the code first and every edit re-runs both installs (~15 min).</details>

❓ **Self-test:** A container starts, logs look perfect, but nothing can reach it. First thing to check?
<details><summary>answer</summary>The bind address. <code>--host 0.0.0.0</code>, not the default <code>127.0.0.1</code> — which inside a container means "only from inside this container", i.e. nobody.</details>

# P1.6 — SHRINK: swap the engine, keep the brain

## P1.6.1 — 💡 A model is not a runtime

This is the idea the whole phase rests on.

| | What it is | Size |
|---|---|---|
| **Model** — `all-MiniLM-L6-v2` | a file of **weights**. The brain. Decides what vectors *mean*. | ~90 MB |
| **Runtime** — `sentence-transformers` + `torch` | the **engine** that executes those weights. Also carries autograd, optimizers, GPU kernels — *training* machinery we never use. | ~1.8 GB |

> 🏆 **Your measured 938 MB RSS was ~90 MB of model and the rest engine. The model was never the problem.**

Swap the engine, keep the brain, and the vectors come out the same.

**ONNX, in MERN terms:**
- A network is just a list of operations (matmul → add → layernorm → …) plus weights.
- **PyTorch** stores the model as *Python classes with `forward()` methods* — so running it needs all of torch to interpret them.
- **ONNX** is a *file format* that writes the operation list down **as flat data**. Self-describing, no Python classes.
- **`onnxruntime`** (17.4 MB) is a small C++ program that reads that list and runs it. That's all it does.

> **PyTorch model = shipping your TypeScript source + the whole compiler to production.**
> **ONNX = shipping the built `bundle.js`.**

⚠️ **The trade:** ONNX is **inference-only and frozen** — you can't train it or poke inside. Perfect here (we never train the embedder). **Wrong for Phase 7**, where you want torch precisely *because* you'll watch gradients flow.

**Model shortlist** (only these four realistically matter):

| Model | Dim | Size | Why |
|---|---|---|---|
| `all-MiniLM-L6-v2` ← ours | 384 | 90MB | fastest, English, the "good enough" default |
| `bge-small-en-v1.5` | 384 | **67MB** | smaller **and** better at retrieval — the free upgrade |
| `bge-base-en-v1.5` | 768 | 210MB | clearly better, 2× vector size |
| `nomic-embed-text` | 768 | 270MB | 8,192-token context — matters only if you stop chunking |

⚠️ **`bge` gotcha:** trained **asymmetrically** — the *query* wants a prefix (`"Represent this sentence for searching relevant passages: "`), passages get none. Forget it and retrieval quietly degrades. Same family as the *vocabulary mismatch* failure from Session 6, except the model has an opinion.
⚠️ Rank on the **Retrieval** sub-leaderboard, not the MTEB headline average (it means across ~8 task types you don't do).

❓ **Self-test:** Your image is 1.95GB and the model weights are 90MB. Where did the other 1.86GB go, and what does that tell you about which one to attack?
<details><summary>answer</summary>Almost all of it is torch — a full training framework shipped to do inference only. Attack the <b>runtime</b>, not the model. Swapping to a smaller model saves ~20MB; swapping the engine saves ~1.8GB.</details>

## P1.6.3a — 🧮 Floating point has a grid

`np.linalg.norm(vec)` → **`0.9999999999999999`**. Read as *"not a unit vector, so I must divide."* **Wrong — that IS 1.0.**

🖼️ A `float64` is not a smooth line. It's a **grid of ticks**, ~16 significant digits apart. Every result snaps to the nearest tick:

```
… ── 0.9999999999999999 ── 1.0 ── 1.0000000000000002 ── …
             ↑ your number
```

There is **no tick in between**. That is one single step below 1.0 — as close as a double can get without being it.

🔢 You already know this in JS: `0.1 + 0.2 === 0.3` → `false` (`0.30000000000000004`). Same IEEE-754 doubles.

✏️ The gap is **machine epsilon**: near 1.0 the spacing is `2⁻⁵³ ≈ 1.11 × 10⁻¹⁶` — 53 mantissa bits. Where it came from: `norm = sqrt(v₀² + … + v₃₈₃²)` is **384 additions**, each snapped to the grid; dust accumulates. Same root cause as `(a+b)+c ≠ a+(b+c)`.

💻 **The lines that matter:**
```python
np.isclose(np.linalg.norm(vecs[0]), 1.0)            # one vector
np.allclose(np.linalg.norm(vecs, axis=1), 1.0)      # all 127 rows; axis=1 = one norm per row
```

⚠️ **Rule: never compare floats with `==`.** Not `norm == 1.0`, not `score == 0.5`. Always a tolerance.
⇒ **fastembed does normalize.** `vecs @ q` stays valid cosine. **Do not divide.** (Dividing by `0.9999999999999999` would change scores by one part in ten quadrillion — real CPU cost, zero effect.)
⇒ And this is *why* the pass bar says "3 decimals" instead of "identical": we predicted this dust before we saw it.

❓ **Self-test:** Why is `if score == 0.5` a bug waiting to happen, and what do you write instead?
<details><summary>answer</summary>Float arithmetic snaps to a grid, so a value that "should" be 0.5 may be 0.4999999999999999 — the <code>==</code> silently never fires. Write <code>np.isclose(score, 0.5)</code> or <code>abs(score - 0.5) &lt; 1e-6</code>.</details>

## P1.6.4 — 🔌 The seam: `service/embedder.py` explained line by line

> 📌 **Written out in full because it did not land in the session. Read this before P1.6.5.**

### The problem it solves

`store.py` currently has the engine **welded in**:

```python
from sentence_transformers import SentenceTransformer   # ← engine, line 1
model = SentenceTransformer("all-MiniLM-L6-v2")         # ← engine
...
vecs = model.encode(embed_texts)                        # ← engine, call site 1
q    = model.encode(query)                              # ← engine, call site 2
```

The chunking logic and the *choice of embedder* are tangled in one file. Want to try ONNX? Edit the store. Want to try the OpenRouter API too? Edit it again, or fork it — and now you have two copies of the chunking logic drifting apart.

**A seam is one function that everything goes through.** The store asks for vectors; it never learns who made them.

> You already build this in Node: `db.js` exports `query()`, and your routes never know whether it's MySQL or Postgres underneath. Same move, different language.

### The file, in three pieces

**1 — load the engine, once**
```python
from fastembed import TextEmbedding
import numpy as np

_model = TextEmbedding("sentence-transformers/all-MiniLM-L6-v2")
```
- `_model` — the leading underscore is Python's convention for *"private, don't reach in from outside."* Nothing enforces it; it's a signal, like naming something `_internal` in JS.
- It's at **module level**, so it runs **once, the first time anything imports this file** — your *"importing a module runs it"* lesson from P1.5.2a, used on purpose this time. Every later import gets the cached module, not a second 90MB load.

**2 — the seam**
```python
def encode(texts):
    single = isinstance(texts, str)
    vecs = np.array(list(_model.embed([texts] if single else texts)))
    return vecs[0] if single else vecs
```

Read it one line at a time:

| Line | What it does |
|---|---|
| `single = isinstance(texts, str)` | *Did the caller hand me one string, or a list of strings?* `isinstance(x, str)` is Python's `typeof x === 'string'`. Stored as a boolean for the two decisions below. |
| `[texts] if single else texts` | fastembed **only accepts a list**. So if we got a lone string, wrap it: `"hi"` → `["hi"]`. This is Python's ternary — read it right-to-left-ish: *"`[texts]` if single, otherwise `texts`."* Same as JS `single ? [texts] : texts`, words reordered. |
| `list(...)` | ⚠️ `_model.embed()` returns a **generator**, not an array — it hasn't computed anything yet, it's a recipe that yields one vector at a time. `list()` drains it. Forget this and you print `<generator object ...>` and wonder what broke. *(Yes — the same generators from your own `week2/7.itergendecorator` notebook, showing up in real library design.)* |
| `np.array(...)` | stacks that list of 1D vectors into one 2D array: 2 texts → shape `(2, 384)`. |
| `return vecs[0] if single else vecs` | **The whole point.** One string in ⇒ hand back one **1D** vector `(384,)`. A list in ⇒ hand back the **2D** matrix `(127, 384)`. |

**3 — the temporary smoke test**
```python
if __name__ == "__main__":
    print(encode("hello").shape, encode(["hello", "world"]).shape)
```
→ `(384,) (2, 384)`

### Why that last line earns its keep

`store.py` calls the encoder **two different ways**, and needs **two different shapes** back:

```python
vecs = model.encode(embed_texts)   # list of 127  → wants (127, 384)
q    = model.encode(query)         # one string   → wants (384,)
scores = vecs @ q                  # (127,384) @ (384,) → (127,)  ✅
```

If `encode("query")` returned `(1, 384)` instead of `(384,)`, that matmul **throws a shape error** — `(127,384) @ (1,384)` doesn't align.

> 💡 **So `encode()` is a drop-in twin of `model.encode`.** Same inputs, same output shapes. That's what lets `store.py` change *who* it calls without changing *how* it calls.

💻 **What P1.6.5 actually changes in `store.py`** — three edits, nothing else:
```python
# delete:  from sentence_transformers import SentenceTransformer
# delete:  model = SentenceTransformer("all-MiniLM-L6-v2")
from .embedder import encode

vecs = encode(embed_texts)   # was model.encode(...)
q    = encode(query)         # was model.encode(...)
```
⚠️ **Your recurring bug, 4th watch: delete the old line first, then type the new one.** Twice now a new assignment landed above an old one that stayed, last-write-wins, **silently**.

💡 **And this is the payoff:** the **OpenRouter `/api/v1/embeddings`** version is now a *third implementation of one function* — swap `_model`, keep everything else. Not a rewrite.

❓ **Self-test:** Why does `encode()` bother returning a different number of dimensions depending on its input, instead of always returning 2D?
<details><summary>answer</summary>So it's a drop-in replacement for <code>sentence-transformers</code>' <code>model.encode</code>, which behaves the same way. <code>store.py</code>'s <code>vecs @ q</code> needs <code>q</code> to be 1D <code>(384,)</code>; a 2D <code>(1,384)</code> would raise a shape error. The seam absorbs the difference so the store needs no changes.</details>

❓ **Self-test:** What is a "seam" and why is one function better than editing `store.py` for each embedder?
<details><summary>answer</summary>A single choke point every caller goes through, hiding which implementation is behind it (like <code>db.js</code> exporting <code>query()</code>). It means swapping engines touches one file instead of forking the chunking logic into drifting copies.</details>

## P1.6.4-redo 🔁 — the three Python mechanics inside `embedder.py`
*(Re-taught at the top of Session 10, at his request: "i didnt understand the new embedder at all." The confusion was the mechanics, not the purpose.)*

💡 **Generators are a recipe, not the food.** `_model.embed(...)` computes **nothing** when called — it returns a generator. `list(...)` is what actually runs ONNX and collects the vectors.

💻 The line that matters:
```python
g = (i * i for i in range(3))
print(g)        # <generator object <genexpr> at 0x...>
print(list(g))  # [0, 1, 4]   ← the model actually runs HERE
print(list(g))  # []          ← one-shot: it's drained
```
| JS | Python |
|---|---|
| `function* gen()` | `def gen(): yield` |
| `[...iterable]` | `list(iterable)` |
| `typeof x === 'string'` | `isinstance(x, str)` |
| `cond ? a : b` | `a if cond else b` ← **reversed** |

⚠️ **Gotcha 1:** a generator is **one-shot**. Second `list()` gives `[]`, silently — no error.
⚠️ **Gotcha 2:** without `list()`, `np.array(generator)` does **not** give `(2, 384)` — NumPy wraps the generator object itself into a useless 0-d array.
⚠️ **Gotcha 3:** Python's ternary reads value-first (`[texts] if single else texts`), the opposite order from JS. Read it aloud as English and it's fine.

💡 **Why `single` exists at all:** `store.py` calls `encode()` **two** ways — line 31 with a *list* of 127 chunks, line 33 with a *single* query string. fastembed only accepts a list. So: **wrap on the way in (line 8), unwrap on the way out (line 9)** — the output shape mirrors the input shape.

<details><summary>❓ Self-test: <code>print(list(g))</code> twice on the same generator — why is the second one <code>[]</code>?</summary>
A generator yields each item once and keeps no history. The first <code>list()</code> drains it to exhaustion; after that it's an empty shell. This is why <code>_model.embed(...)</code>'s result must be consumed exactly once.</details>

<details><summary>❓ Self-test: delete line 9 (<code>return vecs[0] if single else vecs</code>). What breaks, and where?</summary>
A query would come back <code>(1, 384)</code> instead of <code>(384,)</code>. Then <code>vecs @ q</code> in <code>store.py</code> is <code>(127,384) @ (1,384)</code> → shape error. The unwrap is what keeps <code>store.py</code> unchanged.</details>

## P1.6.7a 🧮 — TWO kinds of "not 1"
💡 **Read the *magnitude* of the error, not whether it equals 1.**

| Session 9 | Session 10 |
|---|---|
| `0.9999999999999999` | `0.9998488682752134` |
| off by **1.1e-16** = one grid tick | off by **1.5e-4** = a trillion ticks |
| the computer's dust — ignore it | **your data changed** — go find out why |

The cause: the provider **rounds the numbers to shrink the response** (every value came back an exact multiple of 1/65536). 🖼️ *A 1-metre stick described in whole centimetres — each measurement a hair off, and a shape built from 1,536 of them is a hair off too.*

💻 `vecs = vecs / np.linalg.norm(vecs, axis=1, keepdims=True)` — `axis=1` = length of each **row**; `keepdims=True` = those lengths arrive as a **column beside the table** so each row divides by its own. After it: `unit? True`.

⚠️ Practically the 1.5e-4 changes no ranking — but normalizing is one free line, and it turns "probably fine" into a **contract**.
